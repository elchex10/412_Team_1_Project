# ADR-0001: Web-Based Medical Heart Rate Calculator Architecture

## Status

Accepted

## Team

Giovanni, Erika, Timothy, and Eric

## Context and Problem Statement

Our team is building a Web-Based Medical Heart Rate Calculator. Users enter basic information like their name, age, and gender. The app checks that information, calculates heart rate values, and shows the results to the user.

The main calculation uses the user's age to find their maximum heart rate with the formula 220 - age. The app also calculates a moderate heart rate zone of 50% to 70% and a vigorous heart rate zone of 70% to 85%. The results show up on a dashboard that gives feedback and includes a medical disclaimer.

We needed an architecture that keeps these jobs organized and is realistic for a small student team to build and maintain during the semester. It also had to work with the tools we already picked for the project, which are Node.js, Python 3.14, GitHub, GitHub Copilot, GitHub Actions, and Microsoft Azure.



## Decision Drivers

- Keep the architecture easy for a small team to understand and manage.
- Keep user input, validation, backend logic, calculations, and result display separate.
- Use Node.js and Python 3.14 as the main development technologies.
- Use Microsoft Azure as the planned hosting environment.
- Use GitHub for source control and team collaboration.
- Use GitHub Actions for automated testing, continuous integration, and deployment.
- Use GitHub Copilot as an AI-assisted development tool, with a human checking its work.
- Keep the core heart rate calculations independent from AI availability.
- Have a clear API contract so the team agrees on how data is sent and returned.
- Have an architecture the team can use as a reference in future sprints.

## Considered Options

- A single application with all functionality combined.
- A microservices architecture with independently deployed services.
- A serverless architecture using cloud-managed functions.
- A layered web application that separates the main responsibilities while keeping the overall system simple.

## Decision Outcome

The team chose a layered web application architecture hosted in Microsoft Azure, supported by GitHub-based CI/CD and AI-assisted development through GitHub Copilot.

The system is split into a web interface, input validation, backend application logic, a heart rate calculation engine, and a results dashboard.

The web interface collects the user's name, age, and gender. That input is validated before it goes to the backend. The backend passes the validated information to the calculation functions, which work out the maximum heart rate and the target heart rate zones. The results are then sent

## Consequences

### Positive

- The architecture is simple enough for the team to understand and work with during the semester.
- Keeping the web interface, input validation, backend logic, calculation engine, and results dashboard separate gives each part of the system a clear job.
- The architecture works with the tools the team already chose for the project.
- The heart rate calculations do not depend on AI-generated results.
- GitHub gives the team one place to manage source code, branches, and version control.
- GitHub Actions can help automate testing and deployment when changes are pushed to the repository.
- Microsoft Azure gives the team a consistent hosting environment for the application.
- GitHub Copilot can help with coding and testing, while the team still reviews the suggestions before using them.
- If Copilot is unavailable or a suggestion is rejected, the team can continue through manual coding and review.
- The API contract gives the team a clear format for how heart rate data should be sent and returned.
- Keeping the Graphviz source code in the repository makes the architecture diagram easier to update later.
- The architecture gives the team a shared reference to follow during future sprints.

### Negative

- The components are more connected than they would be in a microservices architecture.
- Individual parts of the application cannot be deployed or scaled separately as easily.
- Using both Node.js and Python 3.14 may require the team to manage more than one development environment.
- Microsoft Azure may require extra setup or troubleshooting during deployment.
- GitHub Actions adds another workflow that the team has to configure and maintain.
- Copilot suggestions still need to be reviewed and cannot replace the team's own understanding of the code.
- The AI component supports the development process instead of providing AI features directly to the user.
- Changes to the API request or response format may require updates in more than one part of the application.
- If the project becomes much larger, the team may need to separate some parts of the system into independent services.
- If the team makes a major architecture change later, it will need to be documented in a new ADR.
