# Eval Pass Threshold and Prompt Versioning

- Status: Accpted
- Deciders: HCDD 412 Team 1
- Date: 2026-11-16
- Tags: evaluations, prompts, ci, safety
- Technical Story: Week 13 team milestone — eval suite in CI

## Context and Problem Statement

The Heart Rate Calculator needs a repeatable evaluation policy so regressions are detected before changes are merged to `main`. The current `evals/cases.jsonl` contains 10 scenarios: happy-path, edge-case, out-of-scope, and adversarial cases. The GitHub Actions workflow runs `python evals/run_evals.py`, and the evaluator exits unsuccessfully when one or more cases fail.

The team also needs a traceable way to identify which assistant instructions were evaluated. The current JSONL `prompt` values are natural-language scenario examples; `evals/run_evals.py` currently sends each case's `query` to the Node API and checks the returned HTTP status and JSON fields. It does not invoke an LLM or evaluate the `policy.must_not_claim` metadata. This ADR therefore establishes the pass/fail policy for the current deterministic API evaluations and a versioning convention for any actual system/developer prompt introduced for the AI component or its mock.

## Decision Drivers

- Prevent regressions in calculation, validation, and out-of-scope behavior.
- Make a failing evaluation a merge-blocking CI failure.
- Keep the evaluation repeatable without requiring a real API key.
- Make it possible to identify the exact prompt instructions associated with an evaluation run.
- Keep prompt and evaluation changes reviewable in Git history.

## Considered Options

- Require a 100% pass rate for all evaluation cases.
- Permit a lower aggregate pass rate, such as 90%, before blocking a merge.
- Run evaluations manually or report failures without making them a required CI check.
- Version prompt instructions in source code or overwrite one shared prompt file for every revision.
- Store immutable, explicitly versioned prompt files and identify the version used by each evaluation run.

## Decision Outcome

Chosen option: **require a 100% pass rate and store actual assistant instructions as immutable, explicitly versioned prompt files**, because the current suite is deterministic and each case represents an expected behavior or boundary. A single failed case can indicate a regression in input validation, calculation output, or refusal to answer outside the calculator's scope. A lower percentage could allow precisely the safety or boundary case that matters to fail while the overall score still passes.

### Evaluation pass threshold

1. The merge-gating evaluation suite must contain at least 10 valid cases and at least one `out_of_scope` case. The current `evals/cases.jsonl` has 10 cases, including two `out_of_scope` cases and two `adversarial` cases.
2. The required pass rate is **100%**: every case must pass every assertion defined for that case. No failed or skipped case is counted as a pass.
3. The evaluator must exit with a non-zero status if any case fails, the case file is invalid, the minimum case count or required category is missing, or the local application cannot start. GitHub Actions must treat that step as required for pull requests targeting `main`.
4. When intended behavior changes, the same pull request must update the affected evaluation cases and expected results with an explanation. A failing case must not be deleted, skipped, or weakened solely to obtain a green CI result.
5. Out-of-scope and adversarial cases remain part of the gate. When the AI component is evaluated for generated text, the evaluator must assert the applicable safety/policy expectations rather than merely storing them as descriptive metadata.

### Prompt versioning

1. Store actual system/developer instructions used by the AI component or its mock under `prompts/`, separate from application code and from the natural-language user examples in `evals/cases.jsonl`. Use an explicit file version, for example `prompts/heart-rate-assistant/1.0.0.md`.
2. Use Semantic Versioning for prompt revisions:
   - **MAJOR** (`2.0.0`): changes the assistant's scope, safety boundaries, or response/input contract in a way that can break existing expectations.
   - **MINOR** (`1.1.0`): adds supported behavior or instructions while retaining the existing contract.
   - **PATCH** (`1.0.1`): clarifies wording or fixes typos without an intended behavior change.
3. Once a prompt version has been used in a merged evaluation run, do not overwrite that file. Create a new versioned file so prior results remain reproducible.
4. Every prompt-dependent evaluation run must record the exact prompt version under test (for example, through a `prompt_version` field in the evaluation metadata or case records). The mock must select an explicit version; it must not silently use an unpinned `latest` prompt.
5. Changes to a prompt and the evaluation cases that verify its behavior must be reviewed and merged together. The evaluation run should report the prompt version alongside its pass/fail summary.
6. Use the local/mock AI implementation for CI and local testing. Do not put API keys, credentials, or real user/health data in prompt files, test fixtures, container images, or the repository.

### Positive Consequences

- A passing CI result means every required deterministic evaluation case passed.
- Out-of-scope and adversarial scenarios cannot be hidden by a high aggregate score.
- Prompt changes are reviewable, traceable, and reproducible against a specific version.
- CI and clean-clone testing do not depend on a paid AI provider or a developer's secret key.

### Negative Consequences

- One failing case blocks a merge, even when the other cases pass; the team must fix the regression or document an intentional behavior change in the same pull request.
- Maintaining immutable prompt versions creates additional files over time.
- A 100% threshold is appropriate for the current deterministic suite; a future nondeterministic model evaluation may need repeated trials and a separately documented policy rather than silently lowering this threshold.

## Pros and Cons of the Options

### 100% pass rate

- Good, because every defined expected behavior must pass before merge.
- Good, because the current evaluator exercises deterministic API responses.
- Bad, because a stale or overly strict fixture can temporarily block unrelated work until it is reviewed and corrected.

### Lower aggregate threshold (for example, 90%)

- Good, because it may tolerate occasional nondeterministic output in a future live-model evaluation.
- Bad, because one of the current 10 cases could fail while the suite still passes, including an out-of-scope or adversarial case.

### Manual or informational-only evaluation

- Good, because it is easy to run without configuring branch protection.
- Bad, because it does not reliably prevent a failing evaluation from merging to `main`.

### Immutable, versioned prompt files

- Good, because a test run can be tied to the exact instructions that produced it.
- Good, because older prompt versions remain available for comparison and rollback.
- Bad, because the team must maintain version metadata and avoid editing previously used prompt files.

### One mutable prompt file or prompt text embedded only in code

- Good, because it initially requires less file organization.
- Bad, because the exact instructions used by an earlier evaluation become harder to identify and reproduce.

## Implementation Notes

The current workflow at `.github/workflows/test.yml` already invokes `python evals/run_evals.py`, and the runner returns a failing exit status when one or more cases fail. Before treating this ADR as fully implemented, update the evaluator to enforce the minimum of 10 cases and the required `out_of_scope` coverage. Also add executable assertions for policy metadata such as `must_not_claim`; the current runner compares the expected HTTP status and response fields but does not evaluate those policy metadata values. Confirm that the evaluation job is configured as a required status check in the repository's branch protection/ruleset for `main`.

The prompt-versioning convention becomes active when the team adds actual system/developer prompt assets for the AI component or mock. Until then, the `prompt` property in `evals/cases.jsonl` should be understood as a natural-language test scenario, not proof that an LLM prompt is being executed.
