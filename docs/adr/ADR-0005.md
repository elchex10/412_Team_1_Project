# ADR-0005: Use Browser localStorage for Calculation History

* Status: proposed
* Date: 2026-10-30
* Deciders: HCDD 412 Team 1

## Context and Problem Statement

During Sprint 2, Team 1 expanded the web-based Heart Rate Calculator to include calculation history. Users need to be able to save previous calculations, view their results, and clear saved history.

The team needed to determine how to store calculation history while keeping the application manageable and avoiding unnecessary infrastructure.

## Decision Drivers

* Allow calculation history to persist after refreshing the page.
* Support saving, viewing, and clearing previous calculations.
* Maintain compatibility with the existing Node.js application.
* Avoid introducing unnecessary backend infrastructure or database dependencies.
* Keep implementation manageable within the Sprint 2 timeline.
* Give users control over removing their saved calculations.

## Considered Options

* **Browser localStorage (Option A):** Store calculation history directly in the user's browser so it persists across page refreshes.
* **Backend database (Option B):** Store calculation history on the server using a database, allowing more advanced storage and retrieval capabilities.
* **Temporary in-memory storage (Option C):** Store calculations only during the current page session, with history disappearing when the page is refreshed.

## Decision Outcome

Chosen option: Browser localStorage.

Team 1 implemented browser localStorage for calculation history during Sprint 2. This approach allows users to save and view previous calculations without requiring a database or additional backend storage.

The application stores calculation results locally in the user's browser and retrieves them when the history section is displayed. Users can also clear their saved history using a dedicated button that requests confirmation before removing the stored calculations.

This decision supports the Sprint 2 user stories while maintaining the simplicity of the existing application.

### Consequences

* **Good:** Calculation history remains available after refreshing the page in the same browser.
* **Good:** No additional database or backend storage infrastructure is required.
* **Good:** The implementation integrates with the existing application and supports the Sprint 2 timeline.
* **Good:** Users can view and clear their saved calculation history.
* **Bad:** Saved history is limited to the browser and device where the calculations were performed.
* **Bad:** Clearing browser data or using private browsing may result in lost calculation history.
* **Bad:** Browser localStorage is not suitable for securely storing sensitive medical information or supporting account-based synchronization.
* **Bad:** Browser storage limits and disabled storage settings may affect availability.
