# ADR-0005: Extend the Heart Rate Calculator with Browser-Based Calculation History

- Status: proposed
- Date: 2026-10-30
- Tags: sprint-2, architecture, frontend, data-persistence

## Context and Problem Statement

During Sprint 1, Team 1 established the foundation of the Heart Rate Calculator through eight user stories focused on input validation, correct heart-rate calculations, displaying current heart-rate information, calculating estimated heart-rate ranges, automated testing, and application deployment.

Building on this foundation, Sprint 2 expanded the application through additional functionality, including heart-rate classification, personalized feedback, visual representations of heart-rate zones, and calculation history.

Issues #26 through #31 represent these Sprint 2 improvements. In particular, Issues #29 and #30 required the application to save successful calculations, display previous results, and allow users to clear their saved history.

The team needed to determine how to retain calculation history after a browser refresh without introducing unnecessary backend database infrastructure.

## Decision Drivers

- Build upon the existing Sprint 1 Heart Rate Calculator functionality.
- Support the additional Sprint 2 user stories without disrupting existing calculations.
- Allow users to review previous successful heart-rate calculations.
- Preserve calculation history after refreshing the browser.
- Prevent invalid calculations from being saved.
- Provide users with the ability to clear their calculation history.
- Maintain a manageable application architecture without introducing unnecessary infrastructure.

## Decision Outcome

Chosen option: Browser Local Storage (`localStorage`).

The team chose browser Local Storage to retain successful heart-rate calculations without requiring a separate database.

This decision supports the Sprint 2 calculation-history requirements while building upon the existing Heart Rate Calculator developed during Sprint 1.

The application stores successful calculation results, including age, current BPM, estimated maximum heart rate, and heart-rate classification. Users can view their saved calculations and clear their history when necessary.

The additional Sprint 2 features, including heart-rate classification, feedback, visualization, and calculation history, are intended to work together with the existing calculation and validation functionality.

## Positive Consequences

- Extends the existing Heart Rate Calculator instead of requiring a separate application.
- Allows users to review previous successful calculations.
- Preserves calculation history across browser refreshes.
- Avoids introducing unnecessary backend database infrastructure.
- Supports the Sprint 2 requirements for viewing and clearing calculation history.
- Builds on the existing frontend and backend structure.
- Provides an opportunity to integrate and test the expanded application as one complete user experience.

## Negative Consequences

- Saved history is associated with the browser and website origin instead of a user account.
- History is not automatically synchronized across different browsers or devices.
- Information can be lost if browser storage is cleared.
- Browser Local Storage is not encrypted and should not be considered secure medical-record storage.
- Additional testing is necessary to ensure the expanded functionality works with the existing calculation and validation features.
