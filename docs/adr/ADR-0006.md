# ADR-0006: Adopt a Trunk-Based Development Strategy with Feature Branches

**Date:** 2026-11-06  
**Status:** Proposed  
**Team:** HCDD 412 — Team 1  
**Project:** Web-Based Medical Heart Rate Calculator

## Context

During our development sprints, team members have worked on different features of the Heart Rate Calculator, including input validation, heart-rate classification, calculation history, and user interface improvements.

As more team members contribute code, we need a consistent branching strategy to prevent conflicting changes, protect the `main` branch, and ensure new functionality is properly reviewed and tested before integration.

For Sprint 3, our team is required to use pull requests, enforce branch protection, and complete code reviews with passing status checks.

## Decision

Our team will adopt a **trunk-based development strategy using short-lived feature branches**.

The `main` branch will serve as the stable, shared version of our application. Team members will create separate branches for individual features, bug fixes, and improvements rather than committing directly to `main`.

Our workflow will follow these practices:

1. **Feature Branches:** Each team member creates a branch from `main` for their assigned GitHub issue.
2. **Pull Requests:** All changes must be submitted through a pull request before merging.
3. **Peer Reviews:** At least one teammate must review and approve each PR. Contributors cannot approve their own changes.
4. **Automated Testing:** Required CI status checks must pass before merging.
5. **Branch Protection:** GitHub branch protection will enforce required reviews and status checks and prevent direct pushes to `main`.
6. **Issue Tracking:** Feature branches and pull requests should reference their corresponding GitHub issues for accountability.
7. **Integration:** Approved changes will be merged into `main`, with the application verified after integration.

For example, Sprint 3 Issue #36 uses branch `feature/36-copy-results` and PR #37 to introduce the Copy Results feature.

## Alternatives Considered

### GitFlow

Provides separate development, release, and hotfix branches. However, this introduces additional complexity for our relatively small project and short sprint cycles.

### Direct Commits to Main

Would simplify development but increase the risk of unreviewed changes, regressions, and conflicts.

### Trunk-Based Development with Feature Branches

Allows team members to work independently while keeping changes small, reviewed, tested, and regularly integrated.

## Consequences

### Positive

- Reduces the risk of introducing unreviewed or broken code.
- Encourages collaboration through peer reviews.
- Helps maintain a stable `main` branch.
- Provides clear accountability through GitHub issues and PRs.
- Supports continuous integration and faster feedback.

### Negative

- Pull request reviews may introduce delays.
- Team members must coordinate when modifying shared files.
- Merge conflicts may occur when multiple branches change the same code.
- Branch protection and CI checks require initial configuration.

## Outcome

This strategy establishes a consistent development process for Sprint 3 and future work. Each team member can contribute independently while maintaining code quality through reviews, automated checks, and controlled integration into `main`.

The team will use GitHub's pull request history, issue tracking, and accountability spreadsheet to document contributions and completed reviews.
