# ADR-0003: Use GitHub Projects for Sprint Planning and Work Tracking

## Status

Proposed

## Team

Giovanni, Erika, Timothy, and Eric

## Context and Problem Statement

Our team is building a Web-Based Medical Heart Rate Calculator, and we need a shared place to plan, assign, and track development work throughout the upcoming sprints. Our previous architectural decisions established GitHub as our repository and collaboration platform, with Microsoft Azure as our planned hosting environment and GitHub Actions supporting automated validation and deployment. For this milestone, we need to choose an agile board that helps the team manage user stories, acceptance criteria, estimates, priorities, and progress while keeping development work connected to the code.

We also need to consider traceability, AI-assisted planning, reporting, cost, and the learning curve for our four-person team. The board should make it easy to see who owns each story, what needs to be completed during Sprint 1, and whether work is ready for review or finished.

## Decision Drivers

* Keep user stories connected to GitHub issues, branches, commits, and pull requests.
* Make Sprint 1 through Sprint 4 work visible in one shared planning location.
* Support AI-assisted story drafting and review while allowing team members to validate and revise AI suggestions.
* Allow the team to assign owners, estimates, priorities, types, and sprint iterations.
* Provide board and backlog views that show work status and help the team prioritize tasks.
* Support reporting and progress reviews using available project views, charts, and relevant metrics.
* Keep the learning curve manageable for a small student development team.
* Minimize the need to switch between separate tools for source code and sprint planning.
* Support a consistent workflow for moving work from To Do through review and completion.
* Keep the setup manageable for the team's remaining work during the semester.

## Considered Options

* GitHub Projects.
* Azure Boards.
* Trello.

## Decision Outcome

Chosen option: GitHub Projects.

The team plans to use GitHub Projects as its shared board for Sprint 1 through Sprint 4 because our application code and repository are already managed in GitHub. GitHub Projects allows the team to organize repository issues and pull requests into configurable views, add custom fields, group work into iterations, and visualize progress. This makes it a suitable choice for tracking stories and connecting planning decisions to implementation work.

The team will use a board view to track story status and a table view to manage the backlog. Custom fields will record estimates, work types, and priorities, while an iteration field will identify the sprint assigned to each item. GitHub issues will contain the user story, acceptance criteria, dependencies, and other implementation details.

The team will also use approved AI tools, including GitHub Copilot and ChatGPT when appropriate, to draft and critique candidate stories and review planning assumptions. AI-generated suggestions will be checked and revised by team members before being accepted into the backlog. The team remains responsible for story scope, estimates, assignments, and sprint commitments.

## Consequences

### Positive

* GitHub Projects keeps planning work closely connected to the repository and its issues and pull requests.
* Each story can have an identifiable owner, estimate, priority, type, acceptance criteria, and sprint assignment.
* Separate backlog and board views help the team organize upcoming work and monitor current progress.
* Iteration fields allow the team to organize and filter work by sprint.
* The team can use existing GitHub collaboration practices instead of introducing a separate planning environment.
* Configurable charts and project insights can help the team review progress and communicate status.
* Built-in workflows can reduce some repetitive board updates when configured appropriately.
* Issues and pull requests provide a clearer record of how planned work relates to code changes.
* The board gives the team a shared reference for planning meetings and Sprint 1 reviews.
* A consistent workflow can help the team identify blocked, unfinished, and completed work.

### Negative

* The initial setup of custom fields, iterations, views, and workflows requires time and coordination.
* Team members must update issue assignments and statuses consistently to keep the board accurate.
* GitHub Projects may require additional configuration or supplementary calculations to track metrics such as velocity and cycle time in the way the team needs.
* The team must learn how project fields, filters, and workflows operate.
* Board information can become inaccurate if changes to code or task status are not reflected in the corresponding issues.
* The team's planning workflow depends on access to GitHub and appropriate repository and project permissions.
* AI-generated stories or estimates may be vague, incorrect, or too large for a one-week sprint, so human review remains necessary.
* Changes to project settings or workflow rules may affect how the team tracks work and should be communicated to all members.

### Follow-up Actions

* Create a GitHub Projects board named `Sprint Board — Team 1`.
* Configure the Estimate field as a number field.
* Configure the Type field with Story, Enabler, and Bug options.
* Configure the Priority field with High, Medium, and Low options.
* Add a Sprint iteration field with one-week iterations, starting Sprint 1 on Saturday, October 17, 2026.
* Configure the Status field with Todo, In Progress, In Review, and Done.
* Create a Backlog table sorted by Priority and a Sprint 1 Board filtered to the Sprint 1 iteration.
* Enable the relevant built-in workflows to update item status when issues close or pull requests merge, where supported by the project configuration.
* Create or update .github/ISSUE\\\\\\\_TEMPLATE/user-story.md so candidate stories follow a consistent format.
* Draft and review candidate user stories with AI assistance, checking acceptance criteria, scope, dependencies, and alignment with the project requirements.
* Add at least eight Sprint 1 stories to the board and give every selected story an owner, estimate, type, priority, acceptance criteria, and sprint assignment.
* Estimate story points as a team and compare task-hour estimates against each member's actual availability.
* Agree on a Sprint 1 goal and make sure it can be demonstrated, remains useful if one story slips, and explains the intended benefit.
* Establish branch naming and pull request practices that connect code changes to the corresponding issues.
* Update the team's accountability spreadsheet to record the ADR and sprint-planning milestone.
* Capture a readable screenshot of the completed Sprint 1 board for the Week 8 assignment submission.
