# ADR-0002: Cloud Platform and Infrastructure as Code Tool Selection

## Status

Accepted

## Team

Giovanni, Erika, Timothy, and Eric

## Context and Problem Statement

Our team is building a Web-Based Medical Heart Rate Calculator, and we need a shared cloud environment where we can deploy and manage the application. 
In ADR-0001, we chose a layered web application architecture with Microsoft Azure as our planned hosting environment.
For this milestone, we needed to decide which cloud platform and Infrastructure as Code (IaC) tool would work best for our project. 
Instead of creating resources manually through the Azure Portal, we need a way to define and provision our environment using code. 
This will help the team maintain a consistent setup and make it easier to track changes throughout the semester.
We also needed to consider the team's experience with the available tools, potential cloud costs, 
student subscription limitations, and how easily everyone could access and contribute to the environment.

## Decision Drivers

- Keep the cloud environment easy for a small team to understand and manage.
- Use a cloud platform that works with the architecture established in ADR-0001.
- Keep potential cloud costs low by using available student resources.
- Choose an IaC tool that the team has already practiced using.
- Provision cloud resources through code instead of manually configuring them.
- Use GitHub to store the infrastructure code and manage changes.
- Make sure all team members can access and contribute to the shared environment.
- Use GitHub Actions to support automated validation and deployment.
- Keep the environment consistent so the team can reproduce it if needed.
- Choose a setup that is realistic for the team to maintain throughout the semester.

## Considered Options

- Microsoft Azure with Bicep.
- Microsoft Azure with Terraform.
- Amazon Web Services (AWS) with CloudFormation.
- AWS with Terraform.

## Decision Outcome

The team chose Microsoft Azure with Bicep as our cloud platform and Infrastructure as Code tool.We decided to use Azure because it was already part of our planned architecture in ADR-0001, and the team has some experience working with it. Azure for Students also provides access to cloud resources through available student credits, which helps us manage costs during the semester.We chose Bicep because the team worked with it during this week's lab, making it a familiar option for creating and managing Azure resources. Bicep allows us to define our cloud environment through code rather than manually creating everything in the Azure Portal.The infrastructure code will be stored in our shared GitHub repository so everyone can review changes and contribute. We will also use GitHub Actions to support automated validation and deployment as the project develops.The team will use a shared Azure resource group, with Contributor access for each member, so everyone can work within the same environment instead of creating separate resources.

## Consequences

### Positive

- Azure works with the architecture and hosting environment we already selected in ADR-0001.
- The team has some experience using Azure and Bicep from previous coursework and this week's lab.
- Bicep allows the team to create and manage cloud resources through code instead of manual configuration.
- Azure for Students provides available cloud credits that can help reduce project costs.
- Keeping the Bicep files in GitHub gives the team one place to manage infrastructure changes.
- The team can review infrastructure updates through GitHub before applying them.
- GitHub Actions can help automate validation and deployment of the infrastructure code.
- Using one shared resource group makes it easier for everyone to work in the same environment.
- The team can reproduce the environment from the Bicep files if resources need to be recreated.
- The decision keeps our cloud setup consistent with the tools and architecture selected for the project.

### Negative

- Choosing Bicep makes the infrastructure code more dependent on Microsoft Azure compared to a tool like Terraform.
- Azure for Students has subscription limitations, so the team needs to be careful about which resources are created.
- Some Azure resources may consume student credits, so costs and resource usage must be monitored.
- Team members may still need additional practice using Bicep and troubleshooting deployment errors.
- Changes to infrastructure code can affect the shared environment if they are not reviewed carefully.
- GitHub Actions will require additional configuration before the team can automate cloud deployments.
- Contributor access allows team members to modify or delete resources, so everyone needs to coordinate changes.
- If the team decides to move to another cloud platform later, the Bicep files would need to be rewritten using another IaC tool.

### Follow-up Actions

- Add the team's Bicep files to the shared GitHub repository.
- Make sure the repository includes the necessary infrastructure code and documentation.
- Validate the Bicep files before provisioning resources.
- Deploy the shared cloud environment using Bicep rather than manually creating resources in Azure.
- Confirm that all four team members have Contributor access to the resource group.
- Add GitHub Actions workflows for infrastructure validation and deployment.
- Monitor resource usage to avoid unnecessary cloud costs.
- Update the ADR if the team changes its cloud platform or IaC tool later.
